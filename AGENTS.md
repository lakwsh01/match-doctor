# AGENTS.md

Rules for any agent or person changing this repository. They are locked: change this file first, in its own commit, before code that breaks a rule.

## Repository

| Path | What | Rule |
| --- | --- | --- |
| `docs/demo/raw/v2/*.json` | Current raw game logs: schema `2.0` plus the v2 extensions in `docs/demo/raw/v2/v2_schema_notes.md` | Read-only input to the report generator. |
| `docs/demo/raw/*.json` | Superseded v1 game logs | Kept for reference. No code reads them. |
| `docs/demo/summary/*.md` | Notes written beside each report | Read-only. |
| `docs/demo/reports/*.json` | Final analytics reports, one per game plus one per match | Generated by `npm run reports` from `raw/v2`. Never edit by hand; change the generator and rerun it. The frontend reads only these. |
| `docs/analytics.md` | What each analytic needs, whether the raw data supports it, and what data is missing | Update it when the generator or raw schema changes. |
| `docs/template/report_sample.json` | Shape sample with fake numbers | Never load it as real data. |
| `web/` | React frontend that displays the reports | All code lives here. |
| `web/public/` | Static files served as-is (the sign-in poster and clip) | The sign-in clip is hardcoded as `/auth-athlete.mp4` (`web/public/auth-athlete.mp4`). Video files stay git-ignored and are never committed. |

The raw schema is described in `README.md`. Raw reports carry only events. Totals, rates, and averages are derived by pure functions in `web/src/lib/`, run by the report generator.

## Stack

- React (latest), TypeScript strict, Vite.
- Runtime dependencies: `react`, `react-dom`, `@supabase/supabase-js` (auth and database), and `@radix-ui/react-popover` (placement, focus, Escape, and outside-click handling for `Select`; hand-written it is hundreds of lines). Adding any other package needs a stated reason in the commit message, and nothing that duplicates a few lines of code we can write.
- Auth and database: Supabase. The browser holds only the project URL and the anon key, read from `web/.env.local` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`; names listed in `web/.env.example`). Never put the service-role key or any other secret in `web/`. Access to data is enforced by Row Level Security, not by the UI.
- Languages: `zh-TW` (default), `zh-CN`, `en-US`. Message dictionaries and the translator are our own code in `lib/i18n/`; no i18n library.
- Styling: CSS Modules plus CSS custom properties. No CSS-in-JS, no utility framework.
- Charts and the court are hand-written SVG components. No chart library.

## Code structure (locked)

```
web/src/
  main.tsx              entry; mounts <App />, imports global styles
  app/                  shell: layout, game selection, wiring features together
  features/<name>/      one folder per screen area (scoreboard, rallies, players, court...)
  components/           reusable, presentational building blocks
  lib/                  pure TypeScript: report types, loading, derivations, formatting, Supabase access
  styles/               tokens.css (design tokens) and global.css (reset, base)
web/scripts/            Node scripts run with plain `node`, no build step; they import lib/ only
```

Import direction is one way. A layer may import only from the layers below it.

```
app  ->  features  ->  components
  \________\________->  lib  <-  scripts
```

- `components/` never imports from `features/`, `app/`, or report types in `lib/report`. It takes plain props (numbers, strings, arrays of plain objects) so it works for any data.
- `features/` may import `components/` and `lib/`. Features never import each other; shared pieces move down to `components/` or `lib/`.
- `lib/` has no React imports and no JSX. Every function is pure: same input, same output, no mutation of its arguments. The exceptions are `lib/report/load.ts`, which reads report files, and `lib/auth/`, which talks to Supabase and keeps its session. Each Supabase area gets its own folder in `lib/`; nothing outside `lib/` imports `@supabase/supabase-js`.
- Files in `lib/` that `scripts/` uses must run under Node's type stripping: runtime imports between them use the `.ts` extension, type imports use `import type`, and no Vite-only APIs (`import.meta.glob`, `import.meta.env`). `scripts/` never imports `lib/auth/`.
- `app/` owns top-level state (session, locale, selected game, rally, player) and passes it down as props. Hooks used only by the app live in `app/`.

## Languages

- Every word a person reads lives in `lib/i18n/messages/<locale>.ts`, one file per locale, all with the same keys (`en-US.ts` defines them; the compiler rejects a locale that misses or adds one). The brand name "Match Doctor" and player ids (`P1`) are not translated.
- No visible string literal in `app/`, `features/`, or `components/`. Features and `app/` ask the translator (`t` for a key, `term` for an id that comes from data, such as a gesture or error type; `term` falls back to the humanized id). Messages hold whole sentences with `{name}` placeholders, never fragments glued in code, because word order differs between languages.
- `components/` stay language-free: they take already-translated strings as props. The one exception is `components/useT.ts`, the context and hook that give `features/` the translator.
- `lib/` returns message keys, ids, and numbers, never prose, except `lib/i18n/`. A `lib/` function that must build a sentence takes the translator as its first argument.
- `app/` owns the locale: state, `localStorage` (`match-doctor.locale`), and `<html lang>`. The default is `zh-TW` for everyone; the browser language is not read. The language `<select>` sits on the sign-in screen and in the report header.
- Reports are language-neutral: ids, numbers, and keys only. A data-quality check ships `id`, counts, and `params`; its title and detail come from the message files. A report ships the game `number`, not a "Game 2" label. Raw event titles (`Men's Doubles Gold, 2026 US Open Pickleball`) are data and stay as logged.
- Adding a language: add its file to `lib/i18n/messages/`, register it in `lib/i18n/locales.ts`. No other code changes.

## Component rules

1. One component per file. File name equals the component name in PascalCase: `StatTile.tsx` exports `StatTile`.
2. Styles sit next to the component as `StatTile.module.css`. A component never styles another component's internals; it passes `className` only if the child accepts one.
3. Named exports only. No default exports, no barrel `index.ts` files.
4. Props are a named `type` above the component (`type StatTileProps = {...}`). No `any`. Optional props only when a real call site omits them.
5. Components are function components without internal data fetching. Data comes in through props; loading happens in `app/` through `lib/`.
6. Local state only for UI concerns (hover, open, active tab). Derived values are computed, not stored in state.

## Minimal and reusable

- Search `components/` and `lib/` before writing anything new. Reuse or extend what exists.
- When a basic component is missing (popover, menu, dialog, tooltip, tabs, and the like), look for a block in the shadcnblocks registry through the `shadcn` MCP server before writing one yourself. The server is declared in `.mcp.json`, the `@shadcnblocks` registry in `web/components.json`, and the key comes from the `SHADCNBLOCKS_API_KEY` environment variable, never from a file in the repo. Take the block's structure, behavior, keyboard handling, and ARIA, then port it to these rules: one function component in `components/` with a named export and plain props, styles in a CSS Module on tokens, no Tailwind class strings, no `components/ui/` folder, no `cn` or `clsx`. Never run `shadcn add` inside `web/`; it writes Tailwind-based files and aliases that break the stack above. A new package the block needs (a Radix primitive, say) needs a stated reason in the commit message. Write the component yourself only when the registry has no fitting block or cannot be reached (server not approved, key missing), and say which in your reply.
- Extract a shared component or function on the second real use, not before. Do not build for imagined callers.
- No dead code, commented-out code, unused props, unused exports, or TODO stubs in a commit.
- No wrapper components that only rename props or forward children.
- Prefer one flexible primitive over several near-copies (`BarList` with a `format` prop, not `SpeedBars` and `ErrorBars`).
- Keep files short. A component past about 120 lines is a sign it should be split.

## Data rules

- Raw report types live in `web/src/lib/report/types.ts` and mirror schema `2.0` with the v2 extensions exactly. Update them only when the schema changes.
- Final report types and builders live in `web/src/lib/report/`: `analysis.ts` builds game and match reports from `contacts.ts` (event joins), `player.ts`, and `quality.ts`. Shared figures (`Rate`, `Dist`, `merge`) live in `web/src/lib/stats.ts`. Every derived figure states its sample size (`Rate` has `made`/`of`, `Dist` has `n`), so match totals merge from game reports without loss.
- Data-quality checks run with the generator and ship inside each final report. A figure built on a failing check is still reported, never silently dropped.
- The frontend loads final reports lazily, one at a time, through `import.meta.glob` over `docs/demo/reports/*.json`. It never loads raw logs. A new raw file must show up in the UI after `npm run reports` with no code change.
- Reports are written as compact JSON. Position tracks ship as `[time_sec, x_m, y_m]` tuples.
- Every derived number (totals, averages, score progression, error splits) is computed by the generator and read from the report. Features only select, format, and render.
- Sign-in defaults to an emailed one-time code; password sign-in is the fallback. An account is a verified Supabase user with `name` in its user metadata: a verified email without one sees "Create account" (name, optional password) before anything else. The app shows the sign-in screen until a session with an account exists. This gate is UI only: report files bundled by `import.meta.glob` are public. Anything that must stay private lives in Supabase behind Row Level Security.
- Players are shown by id (`P1`–`P4`) and team. Never invent player names.
- Court coordinates use the report convention: `x_m` 0–6.096 left to right, `y_m` 0–13.4112 far to near, net at 6.7056.

## Styling rules

- Every color, font, size step, radius, and shadow is a token in `styles/tokens.css`. Module CSS refers to tokens; it holds no raw hex values.
- Layout is web-first: design at desktop width, then make it work down to 375 px with no horizontal scroll.
- Respect `prefers-reduced-motion` for any animation.

## Commands

Run from `web/`:

```bash
npm install
npm run dev
npm run build
npm run reports
```

`npm run reports` rewrites `docs/demo/reports/` from `docs/demo/raw/v2/`. `npm run build` type-checks and builds. It must pass before any commit that touches `web/`.

Before `npm run dev`, copy `web/.env.example` to `web/.env.local` and fill in the Supabase values. `.env.local` is git-ignored; never commit it.

## Commits

- One topic per commit. Plain message, imperative summary line.
- Never commit video files or `web/node_modules`, `web/dist`.
